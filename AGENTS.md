# Cherry Agent Notes

## Terminal Architecture

- `swift run Cherry` uses the embedded Ghostty-backed terminal path:
  `TerminalSurfaceView` -> `GhosttyTerminalContainerView` -> `GhosttySessionBridge` -> `GhosttyTerminal.TerminalView`.
- `TerminalCanvasView` in `TerminalSurface.swift` is the fallback/prototype renderer and input path. Do not assume changes there affect the default running app.
- Local terminal, command and agent tabs default to persistent sessions (Settings › Sessions, `sessions.persistLocal`; `PersistentLocalSessions`). The program runs in a `cherry-host hold` holder process behind the `cherry-host serve` daemon (Rust, `Host/`): the holder owns the PTY and a headless libghostty-vt terminal and answers terminal queries itself. The tab's Ghostty surface is still a native EXEC surface, but its child is the attach adapter `cherry attach … --detach-key none --status-file …` (`HostedSessions.swift`), so typed bytes go Ghostty's encoder → adapter → daemon → holder → PTY, and the adapter repaints from host snapshots (viewport mode when another client makes the grid smaller). The app also keeps one `cherry control` connection per host (`HostControl`) for Create/Kill/List, events, `SendInput` and `Screen`. The adapter's live status file (`TerminalSession.adapterLiveStatus`: attached, viewport, reconnecting) decides whether the surface or the host is the source of screen text, bells and input. Hosted launches skip `/usr/bin/login` (`HostedLaunchSpec`), so exit statuses are real. `usesNativePTYBackend` is true for these tabs too once the adapter runs; use `isPersistentLocalSession` to tell them apart. See `docs/specs/multiplexer-default.md` and `Host/README.md`.
- zsh tabs, native and hosted alike, run Cherry's own zsh bootstrap (its `ZDOTDIR` replaces Ghostty's, so Ghostty's zsh integration never loads; `HostedLaunchSpec` mirrors the native launch, bash and fish get Ghostty's): `cherry-integration.zsh` marks a prompt with OSC 133 A once, from precmd, and zsh's redraw after a resize writes no mark. On resize the holder's terminal (`cherry-vt`, whose screen the adapter's replacements paint) clears such a prompt before a column change reflows it (`Terminal::clear_prompt_for_reflow`, Host/crates/cherry-vt/README.md "Prompts on resize"), so zsh redraws one prompt in place; a native tab has only Ghostty's clear, after the reflow, which can leave the first part of a prompt line the new width wraps.
- The native PTY (`.nativePTY` / `.exec`) path, where Ghostty owns process I/O, terminal state and rendering, is the fallback: the setting is off, or the local host cannot run sessions (disk image, no `cherry` helper, the daemon failed, a session not created within 14 s, or a second copy of the app with the same app identity). A tab whose own Create the host rejected or did not answer in time runs natively too, shows "Not a persistent session: <reason>" with Retry (`persistentFallbackReason`, `PersistentSessionFallbackBar`) and keeps its host for its next launch (`persistentFallbackHosting`: Restart retries persistent once the host takes new tabs, Retry at once); Settings › Sessions shows the last reason (`PersistentSessionsStatus.lastLaunchFailure`). Cherry reads screen text for its content model. The host-managed path and injected test output still use Cherry's terminal buffer; do not assume its parser or output-coalescing delays affect native or persistent Neovim sessions.
- `swift run Cherry` has the installed Cherry's app identity (`Application Support/Cherry`). While Cherry.app runs it is a second copy (`AppInstanceLock`: native tabs, no restore or save); otherwise it restores, saves and ends the user's real tabs and sessions on the shared daemon at `/tmp/cherry-host-$UID/host.sock`. Never shut down, kill or remove sessions on that daemon. For runs of your own use CherryDev.app (`.claude/skills/verify`) or a private `HOME`/`CFFIXED_USER_HOME` with private `CHERRY_HOST_SOCKET` and `CHERRY_CONTROL_SOCKET` (`Scripts/cherry_private_host.py`, whose `stop DIR` tears the run down). The launch argument `-sessions.persistLocal NO` is ignored; pass `'<false/>'`. At launch the instance lock is taken off the main thread (`InstanceLockLaunchWait`): the warm-up, Background Sessions and the first windows wait for it, so a copy launched while the previous one quits shows "Waiting for the previous Cherry to finish quitting…" for up to 12 s; nothing may ask the lock on the main thread before `isResolved` (Dock reopen waits, ⌘Q quits at once, `markQuitting` does nothing).
- Restored windows never show empty. The launch opens the saved windows at once (`ProjectWindowRegistry.savedWindowsLaunchPlan`; only the default window's decision waits 250 ms for a deep link's window), front first (`openLaunchWindows`, `LaunchWindowOrder.frontFirst`: the project most recently active in `ProjectRecencyStore`): the others open together on one main-queue turn (cheaper than one per turn), behind the key window, once the first came on screen, drew its selected tab's text (`LaunchContentFrames`, at most 150 ms) and This Mac's control connection is up (`HostControl.whenConnected`, at most 200 ms; building windows starves its main-actor steps); until they open they count as open in `open-windows.json` (`pendingLaunchWindowRoots`), a quit meanwhile never opens them, and a quit that ends sessions ends their saved tabs' sessions too (`launchWindowHosting`, `localSessionsEndedByAQuit`, `tearDownForQuit`). Tabs no window shows wait to attach until the launch's windows are up (`RestoredTabLaunchQueue.holdBackgroundTabs`, at most 3 s), then until their window's grid settled (see the settled size below). `LaunchWindowCover` makes each window transparent from its first placement (SwiftUI can put a window on screen, empty and at the default size, before its content registers it), and `ProjectWindowReveal` keeps a registered window whose first restore runs (`RepositoryWorkspace.isAwaitingInitialRestore`, `whenInitialRestoreSettles`) transparent and click-through until its tabs, layout and selection are in place, at most 1 s (`windowRevealMaximumWait`, which tests set), after which it shows with "Restoring tabs…" (`WindowRestoringBar`). Nothing in a SwiftUI view update may publish (a window registers from one: `activate` defers its settings writes; `TerminalSession.ghosttyBridge` defers its revision bump; the optimistic tabs below are placed on the restore task's first turn). The app logs its launch phases as `launch: <phase> +<ms since process start> @<epoch seconds>` (`LaunchTimeline`, off in tests), including each surface's first frame with text in a visible window (`first content win=<window number>`, `GhosttySessionBridge.noteLaunchContentFrame`).
- Keys typed during a launch are never lost, and the front window takes them as it shows. `LaunchInteractivity` logs `app active`, `key window` (a launch window is key, usually still transparent) and `interactive` (the app is active, a project window is key and its selected tab's terminal is first responder with a surface); with `CHERRY_LAUNCH_KEY_PROBE=<letter>` (measurements only) it then types that letter (after a Ctrl-U) and logs `key echo … after N ms` once a prompt shows it, or `key echo missing`; `CHERRY_LAUNCH_KEY_PROBE_AT=key-window` types it as soon as a launch window is key, before any terminal exists. `HiddenWindowKeyHold` (`.shared`, set on the registry and `LaunchWindowCover` by the app) holds non-Command keys typed into a window kept off screen (from `LaunchWindowCover` and `ProjectWindowReveal`'s hide) and, from `applicationWillFinishLaunching` until the first window shows (at most 3 s), keys typed with no window key; the reveal posts them back to the front of the event queue in order, after `ProjectWindowRegistry.focusSelectedTerminal` made the selected terminal first responder (a key window showing its terminal, not a note, a to-do or the Omni bar). A persistent or attached tab whose adapter was launched and has not reported attached (`TerminalSession.holdsKeysUntilAdapterAttaches`: its pty is still cooked, where Ctrl-U edits a line the program never sees and Ctrl-C signals the adapter) holds the keys its window's key monitor gets (`GhosttyTerminalContainerView.holdKeyWhileAdapterAttaches`, `holdKeyUntilAdapterAttaches`) until it attached, its launch ended (next turn: then through the host or a new adapter's hold) or `adapterAttachKeyHoldLimit` (3 s) passed, and keys typed behind held ones wait too (`hasKeysAwaitingAdapter`). Command shortcuts are never held. The sweep of abandoned adapter launch directories (`LaunchDirectorySweep`) runs in the background and nothing waits for it (`makeLaunchDirectory` once waited 80–150 ms for it listing a bloated temporary directory). The menu bar item is an AppKit `NSStatusItem` (`MenuBarStatusItem`, its panel `MenuBarPanel`, under the item, menu material, closes on resign key or Escape) made once the launch's windows are open (`CherryAppDelegate.installMenuBarItemOnceLaunchWindowsOpened`): a SwiftUI `MenuBarExtra` makes its status item and window during `applicationDidFinishLaunching` even with `isInserted` false (about 20 ms before the first window opens; that window then pays the window server's one-time setup instead, and the first keystroke's echo comes about 10 ms sooner), a scene cannot be added later, and an `isInserted` binding to an observed object made SwiftUI recurse (`graphDidChange` → `sceneList` → `updateRootHost`) until the stack overflowed as the first window came on screen.
- A persistent tab's session only ever sees its window's settled size: Ghostty starts every surface's child at 800×600 px and applies the view's size about 25 ms later, so the tab writes its surface's grid into the adapter's `--size-file` (`TerminalSession.announceAdapterWindowSize`) and `cherry attach` attaches only once its terminal reports that grid, and sends no Resize while the file says `hold` (`TerminalWindowSettling`: AppKit's will/did full-screen notifications, and a restored window going back to full screen, `ProjectWindowRegistry.enterFullScreen`); each wait gives up after 3 s (`CHERRY_CLI_SIZE_FILE_WAIT_MS`). Create carries the window's settled grid and cell size, so the program starts at the size it is shown at (older hosts ignore the cell): each surface laid out in a window notes its grid in the window's `TerminalWindowGrid` (one per `RepositoryWorkspace`; `GhosttySessionBridge.reportWindowGrid`, also from the in-memory surface a tab shows while its session is created), and `PersistentHostSessions.create(_:configuration:grid:)` asks the tab for its grid last, after connecting and building the launch spec (`TerminalSession.persistentCreateGrid`): it waits until that grid stayed the same for 300 ms while the window is not settling, at most 1 s after the launch (3 s once the window was settling), then takes the tab's own surface's grid, else the window's, else its seed or 120x32 (`TerminalWindowGridWait`, `SessionBackendPolicy.windowGridWait`: `.standard` for the app's windows, This Mac's and devices'; nil in tests' workspaces, which create at once). So a new window's first tab starts at the grid its window settles at, also after a tiling window manager re-tiles the new window (AeroSpace does 90–290 ms after its first layout); a new tab in a window that is open waits for nothing (its window's grid is old); a tab closed meanwhile sends no Create. A restored tab no window shows attaches by the same rule: once the launch releases it, `RestoredTabLaunchQueue` launches its adapter only after its window's grid settled (the tab's `windowGridSource`, `TerminalWindowGridWait.Waiting`; the wait starts at the queue's first look after the hold, so at most the 3 s hold plus 1 s, or 3 s for a settling window; every waiting background tab is looked at each turn, so one window's tabs launch together, still one per turn; shown tabs never wait; `drain()` skips the wait), and its detached surface takes the size the window's terminal had at that grid (`TerminalWindowGrid.Record.size`, noted with the grid, else `mountedTerminalSize`; `TerminalSession.detachedSurfaceSize`, which it keeps until shown), so a window re-tiled after the release gives its program only the final grid. Tests force the race with `RealLocalHost(adapterTerminalStartsAt:)` (its wrapper restores the grid the `--size-file` names after the interim size, not the size it saw at start, which can be Ghostty's first 800×600 px: 35x98 on a CI runner at scale 1), `PersistentLocalRealHostNewWindowsFirstTabsProgramSeesOnlyTheGridItsWindowSettlesAt`, `PersistentLocalRealHostRestoredBackgroundTabAttachesAtTheGridItsWindowSettlesAt` and `persistentLocalWindowGridRestoredTab*`.
- This Mac's windows show their saved persistent tabs before the host answers (`RepositoryWorkspace.showsSavedTabsBeforeHostAnswers`, set by the app for This Mac only: device windows and tests wait as before). On the restore task's first turn the first worktree gets a provisional tab (`TerminalSession.isProvisionalRestore`) for each record `OptimisticRestore.records` allows (owned binding of This Mac, not saved ended or system-ended, no boot, system quit or recorded lost holder since its save, not ended on purpose, not owned or shown by another tab), built from the record with an assumed running `HostedSessionInfo` and `attachmentWithoutListing` (helper from `HostControl.helperExecutableURL`, login environment known now); the window reveals once the saved selection is among them, and the selected tab's `cherry attach` adapter starts at once. The restore (`ControlPlaneRestore`, `WorkspaceRestoreRequest.optimisticTabs`) then applies the usual rules: a record whose session the host lists as the tab's own is confirmed (`confirmProvisionalRestore`: pid, title, sharing; one that ended while Cherry was closed shows its exit and reports nothing; a terminal's clean exit is dropped and its session removed, as before; `WorkspaceRestoreResult.confirmedOptimisticRecordIDs`); any tab the restore built for a record (another session, an ended tab by `SystemEndedSessions`) replaces the provisional one in place (`TerminalWorkspace.replaceRestoredTab`); records kept (host unreachable), dropped, or closed by the user meanwhile lose their provisional tab (`withdrawRestoredTabs`, `.duplicateWindowTeardown`: the session is left alone); pending ones (a second look) keep it until their remainder answers (`RepositoryWorkspace.reconcileOptimisticTabs`). The restore and reconcile find provisional tabs by record id and act only on tabs still provisional: one the user restarted (menu, MCP `restart_process`) is theirs, an open tab like any other; ⌘Z of one closed before the host listed rebuilds it from its closed record (`reopenClosedTab`, provisional while the restore still decides it, `TerminalWorkspace.awaitsRestoreDecision`) and ends nothing. On the step that opens the workspace, every open tab of a saved record is taken out (`takeOutForLayout`) and laid out again with the restore's tabs in the saved order, splits and selection. While provisional, the host's exit events, a disappearance and the adapter's own end are held, not acted on (no close on exit, no restart, no reconnect loop). A restart of the tab clears it.
- Helpers, adapters and new sessions start with the last run's login environment while this run's is captured (`LoginEnvironmentCache`: `login-environment.json` in the identity's Application Support, only the variables Cherry uses (`isPersisted`: PATH, locale, TZ, SSH agent and askpass, shell and account, terminfo, XDG), mode 0600, excluded from backups, read only as this user's own regular file without following a link, written only by the instance-lock holder; not used across a boot, a log out/restart quit in `system-quits.json`, or another login session (the process's own `SSH_AUTH_SOCK` is saved with it and must match); SSH masters never get its agent socket (`HostControl.sshMasterEnvironment`, also `RemoteDeviceShell.app`); `HostedSessionLoginEnvironment.lastRunCache`, which the app sets in `CherryApp.init`). The first `resolve` answers it at once and captures again in the background; everything started before that capture finishes gets the last run's variables, everything after gets the new ones (a connected `HostControl` swaps its `loginEnvironment` via `onRefresh`; its running `cherry control` helper keeps what it started with). A file saved before This Mac booted, or for another shell, is ignored; if this run's shell fails, the last run's capture stays in use; `resolve(retryingNow:)` never answers the last run's capture. Tests never set `lastRunCache` on `.shared`.
- Ghostty routes queued surface messages by surface address, and a replacement surface usually reuses the freed one's address. Freeing a native surface and creating another on the same bridge (one `TerminalController` per bridge) in one main-thread turn can deliver the old surface's pending `child_exited`/`close` to the new one and end its launch; drain with `controller.tick()` in between, as `relaunchNativeSurface` does.
- After init, a native EXEC surface is rebuilt only by `GhosttySessionBridge.relaunchNativeSurface`. Assigning changed options to an EXEC surface (`terminalView.configuration`) rebuilds it, which spawns a child, so `reset()` leaves a native surface's options alone (`startShell` relaunches it).
- Quitting (⌘Q, `osascript … quit`) or closing a project window while local persistent tabs run asks "Keep N sessions running in the background?" (`SessionTeardownQuestion`; Settings › Sessions, `sessions.onQuit`: `ask`, `keep`, `end`), and the answer travels in the close intent (`windowClosed`/`appQuit` keep, `windowClosedEndingSessions`/`appQuitEndingSessions` end), never through the settings. Scripted runs (CherryDev, osascript quits) must launch with `-sessions.onQuit keep` (or `end`) or they wait on that sheet; SIGTERM quits without asking and keeps sessions; a log out, restart, shut down or update asks nothing and ends nothing itself (`CherryAppDelegate.quitReason`; the system then ends sessions at a log out, restart or shut down). A user quit while a window's close question is up is cancelled until it is answered. A quit that keeps sessions, with no busy native program to stop and no session still being ended, exits at once and tears no tab down (`SessionQuitPlan.confirmed`); one that ends sessions or stops native programs orders every window out first, then tears down only native tabs and ending sessions and waits (`CherryAppDelegate.tearDownForQuit`), so the process can outlive its windows by up to 10 s: wait for it to exit before stopping a private host.
- A terminal tab whose own shell exits by itself with status 0 (after `SessionBackendPolicy.cleanExitMinimumRunTime`, 1 s) closes with intent `programExited` (Settings › Sessions, `sessions.closeTabOnExit`), and on a window's last tab the window closes too. `TerminalSession.finishProcessExit` reports it through `programDidExit`, and `TerminalWorkspace.tabProgramDidExit` closes the tab on the next main-loop turn: exits are reported from inside Ghostty's tick (`ingestNativeChildExit`), and closing a tab there would free its surface under Ghostty's stack. Stops, restarts, closes, attached tabs and programs that ended before their tab followed them never report an exit. Workspaces built without a policy (`SessionBackendPolicy.native`) keep exited tabs; `PersistentHarness` uses the app defaults, which close them, so a test that reads an exited terminal of a workspace with other tabs exits it with a non-zero status.
- A saved tab whose session the system ended while Cherry was closed (a restart, crash or log out) comes back as an ended tab (`TerminalSession.systemSessionEnd`, "Ended when the Mac restarted", Restart starts a new session) instead of being dropped; the rule is `SystemEndedSessions` (`WorkspaceStateStore.swift`): the state saved before `kern.boottime`, a log out/restart quit recorded in `Workspaces/system-quits.json` after the save, or the host's `lost_sessions` (holders killed while no daemon ran, copied into `Workspaces/lost-sessions.json`), and never a session this app ended on purpose (`Workspaces/ended-sessions.json`, written by `PersistentLocalSessions.end`, or `sessions-to-end.json`) nor one whose saved record has an `exitStatus` (it comes back as "Session ended (exit N)"). Evidence is per record (`WorkspaceSessionRecord.savedAt`). Restore tests that must see a gone tab dropped save a `savedAt` of now (or none).
- A persistent tab's explicit rename, and an agent's settled task title, reach the host with `Update` (`TerminalSession.syncHostSessionName`, `PersistentLocalSessions.rename`). A session whose holder died is reported with `ended_by: "holder_lost"` (and `holder_log`) on `SessionInfo` and the `exited` event (`HostSessionEnd`): the tab shows "The session host crashed" (`TerminalSession.hostSessionEnd`) and a command is not auto-restarted by it; the daemon ends the program it left (HUP, TERM, KILL). Reconnect Now, Start and MCP `start_process` on a tab whose adapter reports `reconnecting` send it SIGUSR1 (`pokeReconnectingAdapter`) instead of launching a second adapter: the pid is the one the adapter's status file names (`HostedAdapterProcess`, start time checked), never the surface's login(1) wrapper, and a new adapter is launched when that cannot be done. MCP input whose host answer was lost is `input_maybe_delivered`. A tab shows `SharedSessionBar` when its session has other clients or its adapter shows a viewport.
- Every `cherry`/`cherry-host` has a build id (`cherry_protocol::BUILD`): `<YYYYMMDDHHMMSS>.<rev>` only with `CHERRY_BUILD_ID` at build time (`Scripts/install-local-app` sets the app's CFBundleVersion), else `dev-<commit time>.<rev>`, which never orders against another build. The daemon reports it in `Welcome.build` and `Status` (`cherry status [--json]`, which never starts a host), each session its holder's in `SessionInfo.holder_build`; `cherry doctor` checks the local host. Locally, `list`/`new`/`control` (never `attach`) of a newer, explicitly numbered build hand a same-protocol daemon over (`Restart`) only to the daemon's own executable updated in place, never under systemd, and not again for an hour after the old build won (`handover.json`; `cherry-cli/src/handover.rs`). Never set `CHERRY_BUILD_ID` or `CHERRY_TEST_BUILD` for anything that reaches the shared daemon. The daemon writes `host.pid` (with its start identity) and timestamped `… cherry-host[pid] daemon|holder <build>: …` log lines, and rotates `host.log` past 8 MiB under its lock, at start and while it runs; holders follow it (`reopen_if_moved`). Tests use `CHERRY_HOST_TEST_BUILD` (a daemon's, its holders' and `--version`'s build), `CHERRY_HOST_TEST_SERVE_BUILD` (the build of the daemon `cherry-host start` starts), `CHERRY_TEST_BUILD` (the CLI's), `CHERRY_HOST_LOG_MAX_BYTES` and `CHERRY_HOST_LOG_CHECK_MS`.
- The app's session diagnostics go to the unified log (`SessionLog`: subsystem the bundle id, category "Sessions"; `CHERRY_DEBUG_*` traces at debug level, typed or printed content through `debugContent`, which is private), not stderr; tests observe them with `SessionLog.observe`. Settings › Sessions' "Session Host" card is `SessionHostDiagnostics` (runs the bundled `cherry status --json`, `status`, `doctor`, and `restart` only after its alert); tests inject its runner.
- A tab attached to an SSH host's session whose adapter ended `disconnected` or `failed` (unless its status file says `"reconnectable": false`) waits for its host in `HostedReconnects` (the workspace policy's `hostReconnects`; `SessionBackendPolicy.native` has none, so most tests' tabs stay disconnected): one `HostControl.list()` probe per host with the local persistent backoff (0.25 s to 8 s), at once on wake, NWPathMonitor or Retry Now, then `reconnectHostedSession()`; it gives up (`.failed`) on another identity, a protocol mismatch or a session the host no longer lists, and stops its timer after a refused SSH login or host key (`isAuthenticationFailure`, `pausedReasons`) until a wake, network change or Retry Now. A leased `HostControl` treats a protocol mismatch as permanent and waits for `reconnectNow` after a refused login; `availability()` completes without firing once it fails for good. `TerminalSession.isWaitingForHost` drives the bars. A restore that cannot reach an SSH host sets `retryWhenAvailable` to `HostControl.availability()` (a lease until it connects). Tests build `HostedReconnects(monitorsSystem: false)` and call `systemDidWake`/`networkBecameAvailable`.
- Device tabs' ports (docs/specs/remote-devices.md, phase 4a): their Mac reports them (`cherry-host ports --json <SessionInfo.pid>` over the SSH master, `RemotePortScanner`; `TerminalSession.remoteProgramProcessID` is only for that, never a local pid) and `RemotePortForwards` forwards them with `ssh -O forward -L 127.0.0.1:…` on the device's first master (`ClearAllForwardings=yes` does not block it; masters run with `GatewayPorts=no`); forwards are released in `finishClosing` and dropped on `HostSSHMasterManager.masterDidStopNotification`. MCP listing never forwards; only `wait_for_bound_port` with `probe_http` does. Ghostty's `open_url` asks `GhosttySessionBridge.terminalShouldHandleOpenURL` first (`RemoteURLOpening` for a device tab's loopback URLs); tests inject `RemoteURLOpening.opener` and never open a browser.
- Fake-Mac tests (`FakeRemoteMac`) must leave no daemon: teardown calls `HostControl.shutdown()` (final: cancels and kills an attempt under way) before `Scripts/fake-remote-mac stop` (tombstone the shim refuses, repeated kills); a test whose fake Mac has no daemon of its own and needs none uses `makeControl(startsHost: false)` (`cherry control --no-start`).
- Background sessions (this app's own local sessions that no open tab shows) are listed by `BackgroundSessionsModel` (`BackgroundSessions.swift`: the menu bar panel's Background sessions, Cherry › End Background Sessions…, Settings › Sessions) and named once at launch by `BackgroundSessionsNotice`. They must never start a daemon to find out: they read `HostControl.sessions` and connect only once this run reached the host, while `sessions.persistLocal` is on, or while they list sessions. Only this identity's sessions count (never ownerless CLI sessions or another app's), and ending one never rewrites a closed window's saved tabs (its restore, and any restore or adoption while the ending runs, treats it as gone). A background terminal whose shell exited with status 0 is removed, not listed, while *close on exit* is on. Bells and notifications of a background session are posted through `TerminalNotificationCenter.postBackgroundSession` (the model takes them from `PersistentLocalSessions.backgroundSignalHandler`), marked unread in `Workspaces/unread-sessions.json`, and a click opens the session (`open(sessionID:)`); tests inject `postNotification`. Ended sessions no state file names (`WorkspaceStateStore.savedTabsName`, `.bak` copies included), not unread and not host-crashed, are removed after `endedSessionGrace` (10 minutes of active, awake time; tests inject `now` and `isAppActive`), only when `endedSessionsStore` is set. Staged Ghostty resources are kept while any running session's `cherry.resources` tag names them. Tests inject the registry, `OpenHostedTabs`, presenters and UserDefaults, and set `ProjectWindowRegistry.bringWindowForward` so no test window comes on screen.

- Devices (the user's other Macs, `docs/specs/remote-devices.md`, phase 1): `RemoteDeviceStore` (`devices.json` in the identity's Application Support; one writer, the instance-lock holder) keeps them, sets `HostedRemoteHostPaths.shared` and registers one `PersistentHostSessions.remote(…)` per device in `PersistentHostingRegistry`. A window whose project key is `device:<uuid>:/path` (`ProjectLocation`) runs every tab on that hosting (`SessionBackendPolicy.remote`, `RepositoryWorkspace.isRemote`: no git, worktrees, commands or editor), never natively; the device's Cherry shares its daemon, so its sessions (owner `Cherry`) are attached, never adopted, and ours (owner `Cherry@<installation id>`) are never its. A device tab's adapter is relaunched only while its `HostControl` is connected (in batches of at most 8); its typed keys go only over the live connection (`sendKeysOnCurrentConnection`, short timeout; a failure drops the keys queued behind it; `offlineInputRejectedAt`); device windows run no orphan scan (another Mac's clock); a device Cherry no longer knows gets an inert stand-in hosting that leaves saved tabs untouched; only the lock holder changes devices, and Remove forgets only a saved SSH host Add Mac… created; a restore that cannot reach it keeps the records (`HostControl.availability()`) and opens no default shell; each end of a device session is recorded in `sessions-to-end.json` first and finished whenever the app next connects to it (`resumeRecordedEndsOnConnection`), never one whose tab's close can still be undone. Records saved while a device tab's Create ran carry `hostKey`. `RemoteDeviceStore.shared`, `CherryInstallation.shared` and `AppInstanceLock.shared` read the real Application Support: tests never touch them (inject stores, `instanceLock: nil`).
- Installing on a device (phase 2, `RemoteHostInstall.swift`): Add Mac… and Update Session Host… copy this app's own `cherry`/`cherry-host` (`RemoteHostHelpers`, the directory of `HostedSessionClient.installed()`) to `~/Library/Application Support/cherry-host/bin/<build>/` there (tar over ssh into `<build>.partial-<uuid>`, then `xattr -c`, `codesign --verify --strict`, `version --json` and SHA-256 checks, then a rename; never overwrite a build directory) and set the device's `remoteHostPath`, `installedBuild`, `installedArch`. `RemoteHostInstall.decide` is the decision table (absent/same protocol: install; older ≥4: warn and install, the gateway's Replace does the rest; newer or <4: blocked). A same-protocol daemon is handed over (`cherry restart` of the new build) only from one of our own install directories, to a build that is not older, during an install the user asked for; never the other Mac's Cherry.app's. The finish renames with rename(2) (no nesting), uses an existing `<build>` only after checking it (both files, hashes, codesign, runs), replaces a damaged one nothing runs from, else falls back to `<build>-<hash>`; the handover is `cherry restart --if-pid/--if-executable/--if-build` (exit 4 when the daemon changed); after placing, the new build's `cherry-host status --json` rechecks the daemon (newer or <4 refused). Builds are marked `.used-by/<installation id>` by the install, checks and each control connection (`RemoteDeviceStore.markUsedBuild`); GC keeps the current build, the two newest others, anything in use (process, daemon executable/build, holder build), anything marked within 30 days and anything installed within 7 days. A gone cherry-host is `.hostMissing` (Reinstall Session Host…), not offline. `Scripts/build-host` is universal on macOS (needs `rustup target add x86_64-apple-darwin`; `CHERRY_HOST_ARCHS=native` for one arch, said so); `Scripts/check-helper-archs` checks bundles. Tests point a gateway at an install with `HostedRemoteHostPaths.shared.setOverride(_:for:)` (their destination only), never `setResolver`.

- Devices (the user's other Macs, `docs/specs/remote-devices.md`): a device window's key is `device:<uuid>:<path>`, and so are its worktree roots; git runs there through `GitWorktreeService(runner:)` (`RemoteProjectAccess.gitRunner`, `sh -s` over the device's ssh master) and `RepositoryWorkspace.gitPath` turns keys into its paths. ## Keyboard Input

- The embedded Ghostty in-memory backend can bypass `ghostty_surface_key` for direct hardware keys. In particular, unmodified AppKit arrows may be sent directly as bytes by `libghostty-spm` instead of going through Ghostty's encoder.
- Cherry has bridge-level overrides in `GhosttySessionBridge` for host-managed input such as Shift+Enter and unmodified arrows.
- In a project window `AppShortcutMonitor` takes Cherry's ⌘ shortcuts before the terminal sees them: ⌘D is Detach Tab (`SessionCloseCoordinator.detachSelectedTabOrWindow`) and ⌘⇧D is Split Right (Ghostty's own ⌘D/⌘⇧D would split its surface; ⌘⇧D arrives with `charactersIgnoringModifiers` "D"). ⌘W always ends the tab's program and asks "Close “<name>”?" (Close, Detach Instead, Cancel) when that stops a program at work; MCP `close_process` never asks. There is no setting to keep a closed tab's session: detaching keeps it. In a window that stays open, a persistent tab's ⌘W only stops its adapter at first: its session ends when the close can no longer be undone (`ClosedTabHistory`, about 6 s, paused while the toast is hovered or, for 4 s at most (about 10 s in all), while the window is not key), or at once when the window closes or the app quits, so a test or script that closes a tab through the coordinator with a chrome state sees the Kill only then (`closedTabs.endAll()` ends them now). ⌘Z (Edit › Undo) brings the latest closed or detached tab back where it was with its session, but only while no text view is first responder (`ClosedTabUndoRouting`; the window delegate's `windowWillReturnUndoManager` hands AppKit `ClosedTabUndoManager` then, else the window's own text undo manager); `AppShortcutMonitor` takes ⌘Z then, so it never reaches the terminal program.
- The Omni bar (`OmniBarModel.swift`, `OmniBarLive.swift`, `OmniBarView.swift`) is the only palette: ⌘P opens it at its root or closes it, ⌘O and the title-bar project button open it on Projects (`ProjectWindowChromeState.toggleOmniBar`/`showOmniBarProjects`). ⌘K is its action list only while it is open (`AppShortcutMonitor.shortcutAction(omniBarIsOpen:)`, `toggleOmniBarActions`); with the bar closed ⌘K stays Clear Scrollback and the terminal's. Its other keys come from its search field's own commands (`CommandPaletteSearchField.onCommand`), never a key monitor. It lists from cached state only (tabs from `ProjectWindowRegistry`, `BackgroundSessionsModel`, projects and Macs from `ProjectSwitcherLive`; devices are looked at through `RemoteDevicePeeks`, `OmniBarLiveModel.lookAtHosts`) and never connects a host or starts a daemon to list. Rows run through the existing code paths (`OmniBarPerformer`: `ProjectSwitcherActions`, `SessionCloseCoordinator`, the window's sheets); frecency is `OmniFrecencyStore` by row id (it took over `commandPalette.usage.v1`). Its selection is a row id, never empty while there are rows (a query or scope selects the first row; a live update keeps the selected row, else the first), and hover selects only when the pointer itself moves (`OmniPointerTracker`), never when a row moves under it. Editor rows show the app's icon (`OmniItem.appPath`, `OmniAppIconCache`); a tab's detail is its window's project, or at the home folder its directory, "~" at home (`OmniTab.detail`). Matching (`OmniMatcher`) is one contiguous run, or runs that each start a word ("nca" → "New Claude agent"); scattered letters never match. Folders (design E, `OmniBarFolders.swift`, `OmniBarFoldersLive.swift`): at the root, in Projects and in a Mac's scope a query starting with `~/` or `/` (at the root `/` is Worktrees unless pasted or the window has none) lists that Mac's folders (`OmniFolderRows`, `OmniFolderBrowser`: This Mac by FileManager off the main thread, another Mac by `OmniRemoteFolders.listScript` over `sh -s`, only while its control is connected or its master is up, else a Connect row); the folder asked for goes into the script as octal escapes only `printf` decodes, never as shell text. Add Project…/Open Folder… ("… on <Mac>…") are rows (`.browseFolders`) that enter that completion with "~/"; a device folder is added through `RemoteDeviceProjectAdding` (also the Add Project on <Mac>… sheet's), so its key is `device:<uuid>:<path>`. "Not added yet" is `OmniRepositoryScanner` (This Mac every 3 min, devices every 10 min only while connected, cached in `omni-repositories.json` by the instance-lock holder), less projects, `AgentSettings.removedProjectRoots` and a device's hidden projects. Tests build `OmniSources` by hand and drive `OmniBarController`.
- AppKit arrow key events commonly include `.numericPad` and/or `.function`; those should not be treated as user-held modifiers. Only `.shift`, `.control`, `.option`, and `.command` should disqualify an "unmodified arrow" override.
- `git diff` typically runs through `less`, which emits `ESC[?1h ESC=` and expects application cursor keys. Down should be `ESC O B` while application cursor mode is active, not `ESC [ B`.
- ⌘V into a persistent tab whose adapter is away is bracketed as the host reports mode 2004 (`SessionInfo.bracketed_paste`, protocol 7 / holder link 7; `TerminalSession.bracketsPaste`); when the host cannot tell (an older holder) a multi-line paste is bracketed anyway. Clear Scrollback and MCP `clear_output` on a persistent tab also clear the host's history (`ClearHistory`), so MCP reads and the next adapter do not bring it back.
- ⌘V with an image and no text or file URLs is Cherry's: `GhosttySessionBridge.handlePaste` saves it with `PastedImageStore` (`~/Library/Caches/<identity>/Pasted Images`, pruned after 7 days) and pastes its quoted path through `insertPastedText` (the surface brackets it; host-routed input is bracketed per `bracketsPaste`); in a device tab `RemoteFileDropCoordinator` copies it there without asking. File URLs come before text in `PastedContent` (Finder adds the names as text, which paste as before); file URLs with no text (a screenshot tool's copy) paste their quoted paths (`LocalImagePaste.text`). The key monitor takes ⌘V while the terminal view or a view inside it is first responder (`terminalHasKeyboard`). Edit › Paste is `AppTerminalView.paste(_:)`: `pasteHandler` (`GhosttySessionBridge.handleMenuPaste`, as ⌘V), else Ghostty's `paste_from_clipboard`. What the surface pastes by itself (its paste, OSC 52, drops) asks `terminalText(forImageOn:)` (`TerminalSurfacePastedImageDelegate`; an empty answer pastes nothing) when the pasteboard has no text, answering a request made off the main thread on it (`TerminalClipboard.pasteText`). Ghostty's clipboard is `TerminalClipboard.pasteboard` (the container's `pasteboard` follows it). Ctrl+V with an image in a device agent tab, while the agent is in front there, goes through `RemoteClipboardImagePaste` (osascript there, else the path and a toast; Ctrl+V is never swallowed, and the key monitor holds keys typed meanwhile, `GhosttyTerminalContainerView.nativeKeyRoute`). Tests use a private `NSPasteboard(name:)`, never `.general`, and the fake Mac's `osascript` stand-in (never the real one, which sets this Mac's clipboard).
- Keys typed into a persistent tab while its attach adapter is away (relaunching, or reporting that it reconnects; `TerminalSession.keyboardInputGoesThroughHost`) go through the host's `SendInput`, encoded by `HostRoutedKeyEncoder` in `GhosttySessionBridge`; the surface keeps the last screen. The host reports DECCKM (`SessionInfo.application_cursor_keys`) next to the kitty flags, and `TerminalSession.usesApplicationCursorKeys` prefers that report: unmodified arrows, Home and End are `ESC O x` only while DECCKM is on and the kitty flags are 0 (the kitty encoding always sends them as CSI). MCP input the host types is rewritten the same way, `raw_base64` included (`hostTypedInputData`), so it no longer waits for an adapter; the 3 s adapter wait remains only for a host that does not report the field. A session whose holder predates holder link v4 reports false (off or unknown). The encoder also sends F1–F12, modified arrows/Home/End/Page Up/Down/Delete, Control and Control+Option combinations, and Option as Alt per Ghostty's `macos-option-as-alt` (default true: ESC plus the key); under kitty flags it types what Ghostty types for the disambiguate flag (Escape `CSI 27 u`, Control or Alt with a character key `CSI <unshifted code>;m u`, F1/F2/F4 `CSI P/Q/S`, F3 `CSI 13 ~`). Not sent: input-method composition, F13 and above, Option dead keys when Option is not Alt (these reach the dead surface and are lost), and the kitty report-all-keys, alternate-key and associated-text extras.

## Tests

- Prefer `swift test --no-parallel` for a reliable full-suite run.
- Plain `swift test` has shown a parallel-only control-server empty-response flake.
- Session tests run as CI does with `Scripts/test-session-suites unit` and `Scripts/test-session-suites real-host` (the second needs `Scripts/build-host debug`, sets `CHERRY_TEST_HOST_INTEGRATION=1`, and fails on any skipped test). A new session test suite must be named after one of the groups in that script, or added to them. Swift Testing's `--filter` matches source file names as well as test names.
- Rust host checks are under Validation in `Host/README.md`; host and CLI tests always use a private socket and a private `HOME`, and kill the holders they start.
- Device tests: `RemoteDevice*` (unit, fake `cherry control`) and `RemoteDeviceRealHost*` (real helpers through `Scripts/fake-remote-mac`, an `ssh` shim that never runs the real ssh; every local `cherry` there is a wrapper that puts the shim alone on PATH, since Ghostty starts adapters through login(1)). The fake Mac's switches include `arch` (the install scripts call `/usr/bin/codesign` and other tools by absolute path, so a signature failure is tested with a really unsigned copy), and `CHERRY_FAKE_REMOTE_HOST=link|none|newer|old-build` picks its cherry-host at setup (`FakeRemoteMac(name:host:startsDaemon:)`). `Scripts/test-remote-mac-loopback` checks real SSH to 127.0.0.1 with a private sshd and ssh config, and runs `RemoteDeviceRealHostInstallRunsTheRealCopyOverSSH` against it (`CHERRY_TEST_LOOPBACK_SSH`/`_HOME`). Never run a device test against a real host or `~/.ssh`.
