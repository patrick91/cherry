# Cherry Agent Notes

## Terminal Architecture

- `swift run Cherry` uses the embedded Ghostty-backed terminal path:
  `TerminalSurfaceView` -> `GhosttyTerminalContainerView` -> `GhosttySessionBridge` -> `GhosttyTerminal.TerminalView`.
- `TerminalCanvasView` in `TerminalSurface.swift` is the fallback/prototype renderer and input path. Do not assume changes there affect the default running app.
- Local terminal, command and agent tabs default to persistent sessions (Settings › Sessions, `sessions.persistLocal`; `PersistentLocalSessions`). The program runs in a `cherry-host hold` holder process behind the `cherry-host serve` daemon (Rust, `Host/`): the holder owns the PTY and a headless libghostty-vt terminal and answers terminal queries itself. The tab's Ghostty surface is still a native EXEC surface, but its child is the attach adapter `cherry attach … --detach-key none --status-file …` (`HostedSessions.swift`), so typed bytes go Ghostty's encoder → adapter → daemon → holder → PTY, and the adapter repaints from host snapshots (viewport mode when another client makes the grid smaller). The app also keeps one `cherry control` connection per host (`HostControl`) for Create/Kill/List, events, `SendInput` and `Screen`. The adapter's live status file (`TerminalSession.adapterLiveStatus`: attached, viewport, reconnecting) decides whether the surface or the host is the source of screen text, bells and input. Hosted launches skip `/usr/bin/login` (`HostedLaunchSpec`), so exit statuses are real. `usesNativePTYBackend` is true for these tabs too once the adapter runs; use `isPersistentLocalSession` to tell them apart. See `docs/specs/multiplexer-default.md` and `Host/README.md`.
- The native PTY (`.nativePTY` / `.exec`) path, where Ghostty owns process I/O, terminal state and rendering, is the fallback: the setting is off, or the local host cannot run sessions (disk image, no `cherry` helper, the daemon failed, a session not created within 8 s, or a second copy of the app with the same app identity). Cherry reads screen text for its content model. The host-managed path and injected test output still use Cherry's terminal buffer; do not assume its parser or output-coalescing delays affect native or persistent Neovim sessions.
- `swift run Cherry` has the installed Cherry's app identity (`Application Support/Cherry`). While Cherry.app runs it is a second copy (`AppInstanceLock`: native tabs, no restore or save); otherwise it restores, saves and ends the user's real tabs and sessions on the shared daemon at `/tmp/cherry-host-$UID/host.sock`. Never shut down, kill or remove sessions on that daemon. For runs of your own use CherryDev.app (`.claude/skills/verify`) or a private `HOME`/`CFFIXED_USER_HOME` with private `CHERRY_HOST_SOCKET` and `CHERRY_CONTROL_SOCKET` (`Scripts/cherry_private_host.py`, whose `stop DIR` tears the run down). The launch argument `-sessions.persistLocal NO` is ignored; pass `'<false/>'`.
- Ghostty routes queued surface messages by surface address, and a replacement surface usually reuses the freed one's address. Freeing a native surface and creating another on the same bridge (one `TerminalController` per bridge) in one main-thread turn can deliver the old surface's pending `child_exited`/`close` to the new one and end its launch; drain with `controller.tick()` in between, as `relaunchNativeSurface` does.
- After init, a native EXEC surface is rebuilt only by `GhosttySessionBridge.relaunchNativeSurface`. Assigning changed options to an EXEC surface (`terminalView.configuration`) rebuilds it, which spawns a child, so `reset()` leaves a native surface's options alone (`startShell` relaunches it).

## Keyboard Input

- The embedded Ghostty in-memory backend can bypass `ghostty_surface_key` for direct hardware keys. In particular, unmodified AppKit arrows may be sent directly as bytes by `libghostty-spm` instead of going through Ghostty's encoder.
- Cherry has bridge-level overrides in `GhosttySessionBridge` for host-managed input such as Shift+Enter and unmodified arrows.
- AppKit arrow key events commonly include `.numericPad` and/or `.function`; those should not be treated as user-held modifiers. Only `.shift`, `.control`, `.option`, and `.command` should disqualify an "unmodified arrow" override.
- `git diff` typically runs through `less`, which emits `ESC[?1h ESC=` and expects application cursor keys. Down should be `ESC O B` while application cursor mode is active, not `ESC [ B`.
- Keys typed into a persistent tab while its attach adapter is away (relaunching, or reporting that it reconnects; `TerminalSession.keyboardInputGoesThroughHost`) go through the host's `SendInput`, encoded by `HostRoutedKeyEncoder` in `GhosttySessionBridge`; the surface keeps the last screen. The host reports DECCKM (`SessionInfo.application_cursor_keys`) next to the kitty flags, and `TerminalSession.usesApplicationCursorKeys` prefers that report: unmodified arrows, Home and End are `ESC O x` only while DECCKM is on and the kitty flags are 0 (the kitty encoding always sends them as CSI). MCP input the host types is rewritten the same way, `raw_base64` included (`hostTypedInputData`), so it no longer waits for an adapter; the 3 s adapter wait remains only for a host that does not report the field. A session whose holder predates holder link v4 reports false (off or unknown). The encoder also sends F1–F12, modified arrows/Home/End/Page Up/Down/Delete, Control and Control+Option combinations, and Option as Alt per Ghostty's `macos-option-as-alt` (default true: ESC plus the key); under kitty flags it types what Ghostty types for the disambiguate flag (Escape `CSI 27 u`, Control or Alt with a character key `CSI <unshifted code>;m u`, F1/F2/F4 `CSI P/Q/S`, F3 `CSI 13 ~`). Not sent: input-method composition, F13 and above, Option dead keys when Option is not Alt (these reach the dead surface and are lost), and the kitty report-all-keys, alternate-key and associated-text extras.

## Config And Commands

- Agent tool configuration is global in `AgentSettings`.
- Project commands are per project and can be stored locally or in a managed section of `cherry.toml`.
- Use `cherry.toml` for shared project command configuration.

## Tests

- Prefer `swift test --no-parallel` for a reliable full-suite run.
- Plain `swift test` has shown a parallel-only control-server empty-response flake.
- Session tests run as CI does with `Scripts/test-session-suites unit` and `Scripts/test-session-suites real-host` (the second needs `Scripts/build-host debug`, sets `CHERRY_TEST_HOST_INTEGRATION=1`, and fails on any skipped test). A new session test suite must be named after one of the groups in that script, or added to them. Swift Testing's `--filter` matches source file names as well as test names.
- Rust host checks are under Validation in `Host/README.md`; host and CLI tests always use a private socket and a private `HOME`, and kill the holders they start.
