  What it looks like now: while an agent is working, the top layer of the stack breathes between the full glyph color and a soft gray — a 4-second cycle, easing both ways, in both light and dark menu bars. It never quite reaches full brightness, so "working"
  stays distinguishable from idle even at the peak. Orange (needs input) and red (error) are untouched, since those should pop. I rendered the full cycle offline to check it reads smoothly: …/scratchpad/pulse_strip.png if you want to see the frames.

  Why this took more than swapping a color — two findings worth knowing about:

  1. The obvious implementation (a TimelineView in the MenuBarExtra label) livelocks the app at launch: SwiftUI's status-item update loop (requestUpdate → setImage → requestUpdate) never drains inside applicationDidFinishLaunching, so the app pins a core and
  never finishes launching. I caught this because the instrumented build froze, and sample showed the whole main thread stuck in that cycle.
  2. Driving the pulse through MenuBarAgentsModel cost ~11% CPU: since CherryApp holds that model as @StateObject, every alpha publish re-evaluated the entire App body plus the dropdown panel. The pulse now lives in a separate MenuBarPulseModel observed only by
  the status label, quantized to a fixed 16-step alpha table at 4 ticks/s with the baked NSImages cached per step. Measured result: ~3–5% CPU while an agent is working, 0% otherwise (each status-item image swap inherently costs ~1% per tick/s — that's
  SwiftUI/AppKit overhead, and the remaining floor).
   
  If you'd ever want it fully free, the escape hatch is owning the NSStatusItem directly so Core Animation can run on the button's layer (MenuBarExtra snapshots its label to an image, so live animations can't render there) — but that means replacing the
  MenuBarExtra popover plumbing, which I don't think ~4% while-working justifies.
